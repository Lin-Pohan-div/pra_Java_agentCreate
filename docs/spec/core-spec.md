# -lings 練習系統核心規格（core-spec）

| 項目 | 內容 |
| --- | --- |
| 文件版本 | 1.1 |
| 依據實作 | Javalings 0.1.1（見 [profile-java.md](profile-java.md)） |
| 適用對象 | 系統的維護者、重寫者、以及要把本系統移植到其他語言或技術的開發者 |
| 搭配文件 | 每一種語言或技術一份 profile，例如 `profile-java.md` |

## 0. 文件說明

### 0.1 目的與定位

本文件定義「透過修正有問題的程式來學習」這一類練習系統（以下簡稱**本系統**）的行為契約，與實作語言無關。
本系統的使用體驗仿照 Rustlings：學生打開一題刻意寫壞的程式，改到通過檢查，系統自動跳到下一題。

本文件的內容來自 Javalings 0.1.1 的實際行為（as-built），再把語言專屬的部分抽離到 profile。
因此：

- 本文件描述的是**系統現在怎麼運作**，不是理想設計。唯一的例外是 CORE-VER-16（外部資源），它是預留的擴充點，目前沒有參考實作。
- 凡是語言或技術專屬的名稱、數值、檔名、演算法細節，都由 profile 填入；本文件以「由 Profile 定義」標示，並在[附錄 A](#附錄-aprofile-必填參數表)列出所有必填項目。
- 本文件不描述題庫內容（各題的教學目標與錯誤設計）。

### 0.2 文件組成

| 檔案 | 內容 |
| --- | --- |
| `core-spec.md`（本文件） | 語言無關的行為契約，以及 Profile 必填參數表 |
| `profile-<技術>.md` | 某一種技術的實作規格：先填完附錄 A 的參數表，再逐章展開 |

Profile 的章節編號必須與本文件一一對應（第 1 章對第 1 章，依此類推）。

### 0.3 規範用語

| 用語 | 意義 | 對應 RFC 2119 |
| --- | --- | --- |
| **必須**／**不得** | 硬性契約。不符合即視為與本系統不相容。 | MUST／MUST NOT |
| **應**／**不應** | 建議做法。有正當理由時可以偏離，但 profile 必須寫明偏離方式。 | SHOULD／SHOULD NOT |
| **可** | 允許但不要求。 | MAY |

### 0.4 需求編號

- 核心需求：`CORE-<章代碼>-<兩位序號>`，例如 `CORE-VER-03`。
- Profile 需求：`<PROFILE 代碼>-<章代碼>-<兩位序號>`，例如 `JAVA-VER-03`，並以 `→ CORE-VER-03` 標示所實作的核心需求。
- 序號一經發布不重新使用；需求刪除時保留編號並標示「（已移除）」。

| 章 | 章代碼 | 範圍 |
| --- | --- | --- |
| 1 | CLI | 指令列介面：參數解析、練習比對、各指令行為、exit code |
| 2 | PROG | 進度模型：進度檔、掃描重建、下一題選擇、reset 與備份 |
| 3 | VER | 驗證流程：檢查階段、隔離執行、逾時、結果判定 |
| 4 | FMT | 題目格式契約：資料夾結構、中繼資料、略過規則 |
| 5 | KIT | 檢查器函式庫契約：斷言語意、完成宣告、通過標記 |
| 6 | OUT | 終端機輸出：色彩、編碼、替代字、清畫面、表格 |
| 7 | BOOT | 啟動腳本：增量建置、啟動、exit code 傳遞 |
| 8 | TOOL | 出題者工具：自我驗證、套件打包 |

### 0.5 術語

| 術語 | 定義 |
| --- | --- |
| **專案根目錄** | 包含練習目錄的資料夾。進度與備份都存放在這裡。 |
| **練習目錄** | 存放所有題目資料夾的資料夾，預設名稱為 `exercises`。 |
| **練習**（題目） | 練習目錄下一個合法的題目資料夾（見第 4 章）。 |
| **練習 id** | 題目資料夾的名稱，例如 `01_hello`。 |
| **排序值** | 從練習 id 開頭的連續數字解析出的整數；沒有開頭數字時為 0。 |
| **學生可編輯檔** | 學生要修改的檔案。每題一個或多個；個數規則由 Profile 定義。 |
| **檢查器** | 判定學生可編輯檔是否正確的程式（例如測試檔）。學生不應修改它。 |
| **中繼資料檔** | 題目的名稱、難度、主題、提示。 |
| **原題** | 學生可編輯檔在出題時的原始內容，存放在題目資料夾內的原題資料夾。 |
| **參考解答** | 學生可編輯檔的正確版本，存放在專案根目錄的解答資料夾。 |
| **檢查** | 對一題執行全部檢查階段，得到一個結果分類（見第 3 章）。 |
| **檢查階段** | 檢查中的一個步驟，例如建置、測試。由 Profile 宣告。 |
| **產物目錄** | 檢查時寫入建置產物的資料夾，位於題目資料夾內。 |
| **狀態目錄** | 專案根目錄下存放進度檔與備份的資料夾，例如 `.javalings`。 |
| **完成集合** | 進度中記錄為「已完成」的練習 id 集合。 |
| **目前練習** | 進度中記錄的「現在該做的題目」。 |
| **啟動指令** | 學生在終端機輸入以啟動本系統的字串，依作業系統不同（例如 `.\javalings.cmd`）。 |
| **Profile** | 某一種語言或技術對本規格的具體實作設定。 |

## 1. 指令列介面（CLI）

### 1.1 參數解析

**CORE-CLI-01** 系統必須以「啟動指令 [選項…] [指令] [參數…]」的形式接受輸入。選項可以出現在參數列的任何位置。

**CORE-CLI-02** 系統必須支援下列兩個全域選項，並在判斷指令前將它們從參數列移除：

| 選項 | 行為 |
| --- | --- |
| `--no-color` | 關閉色彩輸出（見 CORE-OUT-02）。 |
| `--dir <路徑>` | 以 `<路徑>` 作為練習目錄；專案根目錄改為該路徑的上一層。 |

**CORE-CLI-03** `--dir` 後面沒有接值時（它是最後一個參數），系統不得把它當作選項處理；它會留在參數列中，依一般參數處理。

**CORE-CLI-04** 移除選項後，第一個參數就是指令。指令比對必須不分大小寫。沒有任何參數時，指令必須視為 `welcome`。

**CORE-CLI-05** 指令之後的第一個參數為練習查詢字串（如果該指令接受練習參數）；其餘多出來的參數必須忽略。

### 1.2 專案根目錄的定位

**CORE-CLI-06** 沒有 `--dir` 時，系統必須從目前工作目錄開始，逐層往上尋找含有練習目錄的資料夾，第一個找到的就是專案根目錄。

**CORE-CLI-07** 系統定位專案根目錄時，必須以**目前工作目錄**為起點，而不是啟動腳本所在的位置。

### 1.3 啟動時的檢查順序

系統必須依下列順序執行，任一步失敗即顯示錯誤訊息並以 exit code 1 結束：

**CORE-CLI-08** 1. 定位專案根目錄；找不到時，錯誤訊息必須提示「在專案根目錄執行，或用 `--dir` 指定路徑」。

**CORE-CLI-09** 2. 載入練習（第 4 章）；練習目錄不存在時必須失敗。

**CORE-CLI-10** 3. 載入後沒有任何練習時必須失敗，並在訊息中顯示練習目錄的絕對路徑。

**CORE-CLI-11** 4. 讀取進度（第 2 章）；進度檔無法讀取時必須失敗。

**CORE-CLI-12** 載入練習時，任一題的中繼資料檔格式錯誤，系統必須顯示「<練習 id>/<中繼資料檔名> 格式錯誤：<原因>」，並以 exit code 1 結束；原因必須指出錯誤的位置或性質，不得顯示堆疊追蹤。

**CORE-CLI-43** 載入練習時產生的警告（CORE-FMT-03）必須在啟動檢查完成後、執行指令前，以警告樣式逐條顯示；警告不影響 exit code。

### 1.4 指令一覽

**CORE-CLI-13** 系統必須提供下列指令與別名：

| 指令 | 別名 | 接受練習參數 | 行為章節 |
| --- | --- | --- | --- |
| `welcome` | （無參數時的預設指令） | 否 | 1.6 |
| `help` | `--help`、`-h` | 否 | 1.7 |
| `guide` | | 否 | 1.8 |
| `list` | `ls` | 否 | 1.9 |
| `run` | `r` | 是 | 1.10 |
| `verify` | `v` | 是 | 1.11 |
| `hint` | `h` | 是 | 1.12 |
| `reset` | | 是，或 `--all`／`-a` | 1.13 |
| `version` | `--version`、`-v` | 否 | 1.14 |

注意：`h` 是 `hint` 的別名，`-h` 是 `help` 的別名，兩者不同。

**CORE-CLI-14** 不在上表中的指令必須顯示「未知指令：<指令>」，接著顯示 `help` 的用法說明，並以 exit code 1 結束。

### 1.5 練習查詢

**CORE-CLI-15** 接受練習參數的指令，必須依下列順序比對查詢字串，每一輪都按**載入順序**（第 4 章）走訪所有練習，並傳回第一個符合者：

1. 練習 id 完全相同（不分大小寫）。
2. 練習 id 以查詢字串開頭（不分大小寫），例如 `15` 符合 `15_recursion`。
3. 題目名稱包含查詢字串，或任一主題標籤包含查詢字串（不分大小寫）。

**CORE-CLI-16** 沒有給練習參數時，目標必須是目前練習；目前練習不在練習集合中時，目標為載入順序的第一題。

**CORE-CLI-17** 有給查詢字串但沒有任何練習符合時，系統必須顯示「找不到練習：<參數列>」，並以 exit code 1 結束。

**CORE-CLI-18** 系統顯示練習時，標題格式必須為「<練習 id> — <題目名稱>」。

### 1.6 `welcome`

**CORE-CLI-19** `welcome` 必須依序顯示：工具名稱與版本、一句工具簡介、目前進度（「已完成數/練習總數 完成」）、目前練習的標題與學生可編輯檔的絕對路徑、常用指令（run、hint、list）的簡短說明、以及 `guide` 與 `help` 的啟動指令提示。

**CORE-CLI-20** `welcome` 不得修改進度檔。

### 1.7 `help`

**CORE-CLI-21** `help` 必須顯示用法 `<啟動指令> [指令] [練習 id]`、每個指令一行的說明（run、verify、list、hint、reset、reset --all、guide、help、version），以及全域選項的說明。用法說明中不列出別名與 `welcome`。

### 1.8 `guide`

**CORE-CLI-22** `guide` 必須依序顯示下列段落：怎麼玩、你現在要改（目前練習的學生可編輯檔絕對路徑，並提醒不要修改檢查器）、用 run 監看（含逾時秒數與離開方式）、卡住了怎麼辦（看錯誤訊息、hint、參考解答）、常見問題（色彩、進度檔位置、reset 與 reset --all 的差別）。

**CORE-CLI-23** `guide` 中出現的指令必須使用當前作業系統的啟動指令；逾時秒數必須取自 Profile 設定值，不得寫死。

### 1.9 `list`

**CORE-CLI-24** `list` 必須以表格（CORE-OUT-09）列出所有練習，欄位依序為「狀態、練習、難度、主題」，列的順序為載入順序。

**CORE-CLI-25** 狀態欄必須為下列三者之一，判斷優先順序由上而下：

| 條件 | 顯示 | 色彩 |
| --- | --- | --- |
| 在完成集合中 | `✓ 完成` | 綠 |
| 是目前練習 | `→ 目前` | 黃 |
| 其他 | `  待做` | 無 |

**CORE-CLI-26** 主題欄必須以「, 」連接所有主題標籤。表格之後必須顯示「共 <練習總數> 題，已完成 <完成集合大小> 題。」

### 1.10 `run`（監看模式）

**CORE-CLI-27** `run` 不帶練習參數時，必須先執行進度掃描（CORE-PROG-11），再以目前練習為目標；帶練習參數時，必須跳過掃描，直接以該練習為目標。

**CORE-CLI-28** `run` 必須反覆執行下列循環：

1. 需要清畫面時清除畫面（CORE-OUT-08）。
2. 記下目標練習學生可編輯檔的修改時間。
3. 以互動模式檢查目標練習（CORE-VER-13）。
4. 通過時：
   - 如果所有練習都已完成，結束 `run`，exit code 0。
   - 否則把目標換成新的目前練習（即 CORE-PROG-09 選出的下一題），顯示一條分隔線，**不清畫面**，立即回到步驟 2 檢查下一題。
5. 未通過時：顯示「監看中：存檔後會自動重新檢查（Ctrl+C 離開）」，等待學生可編輯檔變更（CORE-CLI-29），然後回到步驟 1 並清畫面。

**CORE-CLI-29** 系統判斷檔案變更的方式，必須是定期輪詢學生可編輯檔的修改時間，直到它和步驟 2 記下的值不同。輪詢間隔由 Profile 定義。輪詢時檔案暫時不存在（編輯器存檔過程中常見），必須視為「尚未變更」並繼續等待。

**CORE-CLI-30** 系統監看的對象只有學生可編輯檔；檢查器或中繼資料變更不得觸發重新檢查。

**CORE-CLI-31** `run` 除了全部完成之外，不會自行結束；使用者以中斷訊號（Ctrl+C）離開。`run` 不應用於 CI。

### 1.11 `verify`

**CORE-CLI-32** `verify` 必須以非互動模式檢查目標練習一次（CORE-VER-13）。通過時 exit code 必須為 0；其他任何結果的 exit code 必須為 1。

**CORE-CLI-33** `verify` 不得執行進度掃描。`verify` 對進度的影響與 `run` 相同：檢查前把目標設為目前練習；通過時記錄完成並推進目前練習（CORE-PROG-07、CORE-PROG-08）。

### 1.12 `hint`

**CORE-CLI-34** `hint` 必須顯示「提示 — <練習標題>」，接著逐行顯示提示內容（每行縮排兩格），最後顯示「卡住了就執行 <啟動指令> reset <練習 id> 拿回原始碼。」

**CORE-CLI-35** 提示內容為空白時，必須只顯示「（這題沒有額外提示）」，不顯示 reset 的提示。

**CORE-CLI-36** `hint` 不得修改進度檔。

### 1.13 `reset`

**CORE-CLI-37** `reset <練習>`（或不帶參數，表示目前練習）必須依序：把該題移出完成集合、設為目前練習、儲存進度、顯示「已將 <標題> 標記為未完成。」，然後執行原題還原（CORE-PROG-13）。

**CORE-CLI-38** `reset --all`（或 `reset -a`）必須依序：清空完成集合、刪除所有練習的產物目錄、把目前練習設為載入順序的第一題、儲存進度，然後顯示「已清除 <清除前的完成數> 題的進度，回到起點。」以及「原始碼沒有被還原」的說明。

**CORE-CLI-39** `reset --all` 不得還原或修改任何學生可編輯檔。

**CORE-CLI-40** `--all`／`-a` 必須是 `reset` 之後的第一個參數才會生效；在其他位置時會被當成練習查詢字串。

### 1.14 `version`

**CORE-CLI-41** `version` 必須只輸出一行「<工具名稱> <版本>」。

### 1.15 Exit code 總表

**CORE-CLI-42** 系統必須依下表結束：

| 情況 | exit code |
| --- | --- |
| 指令正常完成（含 `run` 全部完成、`reset` 找不到原題而只顯示警告） | 0 |
| `verify` 未通過 | 1 |
| 啟動檢查失敗（CORE-CLI-08 ～ CORE-CLI-11） | 1 |
| 未知指令 | 1 |
| 找不到指定的練習 | 1 |
| 進度檔寫入失敗（顯示「進度檔寫入失敗：<原因>」） | 1 |
| 中繼資料格式錯誤（CORE-CLI-12） | 1 |
| `run` 被使用者中斷 | 由執行環境決定 |

## 2. 進度模型（PROG）

### 2.1 進度檔

**CORE-PROG-01** 進度檔必須存放在 `<專案根目錄>/<狀態目錄>/progress.txt`。使用 `--dir` 時，專案根目錄為練習目錄的上一層（CORE-CLI-02）。

**CORE-PROG-02** 進度檔必須是 UTF-8 純文字，以 LF 換行，格式如下：

```
# <工具代號> progress - 請勿手動編輯
current:<目前練習 id>
done:<練習 id>
done:<練習 id>
…
```

- 第一行是註解，內容由 Profile 定義。
- `current:` 恰好一行；沒有目前練習時，冒號後為空字串。
- `done:` 每個已完成練習一行，順序為**加入完成集合的先後**。

**CORE-PROG-03** 讀取進度檔時，系統必須：

- 對每一行去除前後空白後判斷前綴；以 `current:` 開頭者取其後內容（去除空白）為目前練習，多行時以最後一行為準；以 `done:` 開頭者把其後內容（去除空白）加入完成集合；其他行一律忽略。
- 進度檔不存在時，視為完成集合為空、沒有目前練習。

**CORE-PROG-04** 讀入後，系統必須從完成集合中移除不屬於目前練習集合的 id（例如題目已刪除、改名，或因 CORE-FMT-03 被略過）。被移除的 id 不得計入已完成數，並在下次儲存時從進度檔中消失。

**CORE-PROG-05** 讀取後，如果目前練習為空，或不是現有的練習 id，系統必須把目前練習設為「載入順序中第一個不在完成集合的練習」；全部都在完成集合時，設為載入順序的第一題。此修正只在記憶體中生效，直到下一次儲存。

**CORE-PROG-06** 儲存進度時，系統必須建立狀態目錄（如果不存在），並以完整內容覆寫進度檔。

### 2.2 檢查對進度的影響

**CORE-PROG-07** 每次檢查開始前，系統必須把目標練習設為目前練習並立即儲存；即使檢查最後失敗，目前練習也維持為該題。

**CORE-PROG-08** 檢查通過時，系統必須依序：

1. 把該題加入完成集合；如果是**第一次**加入，顯示「恭喜完成第 <完成集合大小> 題！」。
2. 以 CORE-PROG-09 選出下一題：有的話設為目前練習，並顯示下一題的標題與學生可編輯檔路徑；沒有的話顯示「全部練習都完成了」的訊息，目前練習維持不變。
3. 儲存進度。

**CORE-PROG-09** 下一題的選擇方式：把所有練習依**排序值**由小到大排列（排序值相同者維持載入順序），從剛通過的那一題的**下一個位置**開始往後找第一個不在完成集合中的練習；找到最後還沒有，就從頭繞回來，直到回到剛通過的那一題為止。找不到則表示全部完成。

### 2.3 進度掃描

**CORE-PROG-10** 進度掃描的目的，是依檔案的實際狀態重建完成集合，讓進度檔遺失或過期時不影響使用。

**CORE-PROG-11** 進度掃描必須依排序值的順序，對每一題：

| 條件 | 處理 |
| --- | --- |
| 原題存在、學生可編輯檔存在，且兩者逐位元組完全相同（「未修改」） | 移出完成集合，不執行檢查 |
| 其他情況（含找不到原題） | 執行完整檢查（第 3 章，不顯示結果）：通過則加入完成集合，否則移出完成集合 |

Profile 規定一題有多個學生可編輯檔時，必須**全部**都和各自的原題相同，才算「未修改」。

**CORE-PROG-12** 掃描期間，系統應在同一行顯示並更新「掃描進度中… <第幾題>/<總題數>」，結束時清除該行。掃描完成後，系統必須把目前練習設為排序值順序中第一個未完成的練習（全部完成時維持原值），然後儲存進度。

### 2.4 原題還原與備份

**CORE-PROG-13** 原題還原必須對該題每一個學生可編輯檔依序判斷：

| 條件 | 處理 | 訊息 |
| --- | --- | --- |
| 原題不存在 | 不還原，結束 | 警告：「找不到原題 <原題路徑>，原始碼沒有還原。」 |
| 學生可編輯檔存在且與原題完全相同 | 不還原，結束 | 「<檔名> 本來就是原題，不需要還原。」 |
| 學生可編輯檔存在且不同 | 先備份，再以原題覆蓋 | 「你改過的版本已備份到 <備份路徑>」、「已將 <檔名> 還原成原題。」 |
| 學生可編輯檔不存在 | 直接以原題建立 | 「已將 <檔名> 還原成原題。」 |

**CORE-PROG-14** 備份必須存放在 `<專案根目錄>/<狀態目錄>/backup/<練習 id>/<檔名>`。每題每個檔案只保留最後一份備份，新備份直接覆蓋舊的。

### 2.5 不做的事

**CORE-PROG-15** 系統不記錄完成時間、嘗試次數或任何統計資料。

## 3. 驗證流程（VER）

### 3.1 檢查階段

**CORE-VER-01** 一次檢查的輸入是一個練習，包含它的學生可編輯檔、檢查器，以及 Profile 宣告的檢查階段清單。

**CORE-VER-02** Profile 必須宣告**有序的**檢查階段清單。每個階段必須宣告：名稱、執行方式、失敗時歸入的結果分類（CORE-VER-08）、以及是否受逾時限制。

**CORE-VER-03** 檢查階段必須依宣告順序執行；任一階段失敗時，後續階段必須不執行，並以該階段的結果作為檢查結果。

**CORE-VER-04** 每個階段的成功或失敗，必須只依可觀察的訊號判定：exit code、輸出中的標記、是否逾時，或工具 API 回傳的成功旗標與診斷清單。

### 3.2 產物與隔離

**CORE-VER-05** 每一題的建置產物必須寫入該題的產物目錄。每次檢查開始時，系統必須先清空產物目錄，避免殘留的舊產物影響結果；個別檔案刪除失敗（例如被鎖住）時應略過，不中止檢查。

**CORE-VER-06** 執行檢查器的階段，必須在與本系統不同的作業系統行程中執行，使學生程式的無窮迴圈、當機或強制結束不會影響本系統。

**CORE-VER-07** 檢查不得修改學生可編輯檔、檢查器、中繼資料檔或原題。

### 3.3 結果分類

**CORE-VER-08** 每次檢查必須得到下列四種結果之一：

| 分類 | 意義 |
| --- | --- |
| **通過** | 所有階段都成功。 |
| **建置失敗** | 建置類階段（例如編譯）失敗，程式還不能執行。附帶診斷清單。 |
| **測試失敗** | 程式可以執行，但檢查器判定不通過。附帶檢查器輸出。 |
| **內部錯誤** | 檢查本身無法正常完成，包括逾時。附帶說明訊息與已擷取的輸出。 |

**CORE-VER-09** 測試階段要判定為通過，必須**同時**滿足：沒有逾時、行程 exit code 為 0、輸出中含有通過標記（CORE-KIT-03）。缺少任何一項就不算通過。

**CORE-VER-10** 測試階段逾時時，結果必須是「內部錯誤」，訊息必須說明逾時秒數與「可能有無窮迴圈」。測試階段沒逾時但不通過時，結果必須是「測試失敗」。

### 3.4 逾時與輸出擷取

**CORE-VER-11** 執行檢查器的階段必須有逾時上限，數值由 Profile 定義。逾時時，系統必須強制終止該行程，並保留逾時前已擷取的輸出。

**CORE-VER-12** 系統必須把檢查器行程的標準輸出與標準錯誤合併擷取，而且讀取方式不得阻塞逾時判定（例如在另一條執行緒中讀取），即使學生程式陷入不輸出任何內容的無窮迴圈，逾時仍然有效。

### 3.5 結果顯示

**CORE-VER-13** 檢查分為兩種模式：

- **互動模式**（`run`）：檢查前顯示「檢查中: <練習標題>」與學生可編輯檔的絕對路徑。
- **非互動模式**（`verify`）：不顯示上述標頭。
- 進度掃描（CORE-PROG-11）：不顯示任何結果。

**CORE-VER-14** 顯示給學生的檢查器輸出，必須先經過清理：去除空白行、內容等於通過標記的行、以失敗標記開頭的行，最後去除整體前後空白。

**CORE-VER-15** 各結果分類必須依下表顯示（區塊標題以粗體顯示，區塊內每行縮排兩格）：

| 分類 | 顯示內容 |
| --- | --- |
| 通過 | 成功訊息「✓ <標題> 通過！」；清理後的輸出不為空時，加上「輸出」區塊；接著是 CORE-PROG-08 的訊息。 |
| 建置失敗 | 錯誤訊息「✗ 編譯失敗，程式還不能跑。」；「編譯錯誤」區塊列出所有診斷；提示「閱讀錯誤訊息中的檔名與行號。」 |
| 測試失敗 | 錯誤訊息「✗ 可以編譯，但測試沒通過。」；清理後的輸出不為空時，加上「測試輸出」區塊；為空時改為以次要說明樣式顯示「測試沒有輸出結果，可能缺少 <完成宣告>。」；最後提示「測試已經寫好了，去調整 <學生可編輯檔名> 讓輸出符合預期。」 |
| 內部錯誤 | 錯誤訊息「✗ <說明訊息>」；清理後的輸出不為空時，加上「輸出」區塊。 |

### 3.6 外部資源

> 本節是**擴充點**，為 JDBC、Spring 這類需要外部資源的題目預留，**目前沒有參考實作**（Java profile 不使用）。
> 這是本文件中唯一不是從現有程式碼歸納出來的需求。第一個需要它的 profile 必須補上具體做法，並在實作後回頭修訂本節。

**CORE-VER-16** Profile 或個別練習**可**宣告檢查所需的外部資源（例如資料庫、伺服器）。不需要外部資源的 profile 必須在 P-18 填「不適用」，而且不需要實作本節。有宣告時：

- 系統必須在第一個檢查階段之前完成資源的前置準備；準備失敗時，結果為「內部錯誤」。
- 系統必須在檢查結束後（不論結果）執行資源清理。
- 資源的種類、準備與清理的方式，全部由 Profile 定義。

## 4. 題目格式契約（FMT）

### 4.1 練習目錄與載入

**CORE-FMT-01** 練習目錄不存在或不是資料夾時，載入必須失敗（CORE-CLI-09）。

**CORE-FMT-02** 系統必須把練習目錄下每一個**直接子資料夾**都當成候選題目，但名稱以 `.` 開頭的資料夾除外。候選題目必須依資料夾名稱的字串順序排列，這就是**載入順序**。

**CORE-FMT-03** 候選題目依下列規則判斷是否收錄：

| 情況 | 處理 |
| --- | --- |
| 缺少中繼資料檔、學生可編輯檔或檢查器 | **直接略過，不報錯**（容許放置未完成的題目資料夾） |
| 學生可編輯檔或檢查器的個數超過 Profile 的規定 | **略過並產生警告**「略過 <練習 id>：<原因與實際個數>」（CORE-CLI-43），不得自行挑選其中一個 |
| 其他 | 收錄 |

系統判斷個數時，必須先確認三項都存在；三項俱全時才檢查個數。

**CORE-FMT-04** 練習 id 必須等於題目資料夾的名稱；排序值必須取 id 開頭的連續數字，沒有開頭數字時為 0。

### 4.2 題目資料夾

**CORE-FMT-05** 一個合法的題目資料夾，必須包含下列內容（實際檔名由 Profile 定義）：

```
<練習目錄>/<練習 id>/
  <中繼資料檔>          必要
  <學生可編輯檔>…        必要，一個或多個（個數規則由 Profile 定義）
  <檢查器>              必要
  <原題資料夾>/
    <原題檔>…            reset 與進度掃描使用；缺少時不影響載入
  <產物目錄>/            系統自動產生，不納入版本控制
```

**CORE-FMT-06** 系統辨識學生可編輯檔與檢查器時，只看題目資料夾的**直接檔案**，不往子資料夾找。辨識規則由 Profile 定義。

**CORE-FMT-07** 每一個學生可編輯檔必須在原題資料夾中有一個對應的原題檔，命名規則由 Profile 定義。原題檔的命名必須讓辨識規則（CORE-FMT-06）與學生的編輯器都不會把它當成第二個可編輯檔或原始碼。

**CORE-FMT-08** 參考解答必須存放在 `<專案根目錄>/solutions/<練習 id>/`，檔名與學生可編輯檔相同。執行期的 CLI 不讀取參考解答；只有出題者工具（第 8 章）會用到。

### 4.3 中繼資料

**CORE-FMT-09** 中繼資料檔必須是 JSON 物件，欄位如下：

| 欄位 | 型別 | 缺少時的預設值 | 用途 |
| --- | --- | --- | --- |
| `name` | 字串 | 練習 id | 題目名稱，用於標題與查詢 |
| `difficulty` | 字串 | `"★"` | 難度，慣例為 1～5 顆 `★` |
| `topics` | 字串陣列 | 空陣列 | 主題標籤，用於 `list` 與查詢 |
| `hint` | 字串 | 空字串 | 提示，以 `\n` 分行 |

**CORE-FMT-10** 未定義的欄位必須忽略。根值不是物件時，所有欄位必須套用預設值。非字串的欄位值必須轉成字串使用（轉換方式由 Profile 定義）。`topics` 不是陣列時，必須把它轉成字串，作為唯一的主題標籤。

**CORE-FMT-11** 中繼資料檔必須以 UTF-8 讀取。

### 4.4 擴充

**CORE-FMT-12** 新增題目時，只要在練習目錄下加入合法的題目資料夾，系統就必須自動收錄，不需要修改任何設定或程式。

## 5. 檢查器函式庫契約（KIT）

本章規範隨系統提供、供檢查器使用的斷言函式庫（以下簡稱**檢查器函式庫**）。Profile 可以改用該技術既有的測試框架，但必須滿足本章的可觀察行為。

### 5.1 通過與失敗的回報

**CORE-KIT-01** 檢查器必須在所有斷言都成功後，**顯式**呼叫完成宣告（例如 `done()`）。只有完成宣告會輸出通過標記；漏寫完成宣告的檢查器永遠不會通過。

**CORE-KIT-02** 任何一個斷言失敗時，檢查器必須立刻中止後續斷言，並讓行程以非 0 的 exit code 結束。

**CORE-KIT-03** 通過標記必須是一行獨立輸出到標準輸出的固定字串，並在輸出後立即 flush。標記字串由 Profile 定義，而且必須是學生程式不太可能剛好印出的字串。

**CORE-KIT-04** Profile 可以另外定義失敗標記前綴；這類行在顯示時會被清掉（CORE-VER-14）。檢查器函式庫不一定要輸出失敗標記。

### 5.2 斷言

**CORE-KIT-05** 檢查器函式庫必須至少提供下列語意的斷言：

| 斷言 | 通過條件 |
| --- | --- |
| 相等 | 期望值與實際值相等；陣列或序列必須逐元素（含巢狀）比較，不得只比較參考 |
| 為真／為假 | 布林值為 true／false |
| 浮點數接近 | 兩數差的絕對值不大於容許誤差（容許誤差由 Profile 定義） |
| 非空值 | 值不是 null（或該技術的等價物） |
| 拋出例外 | 執行的程式碼拋出指定類型（或其子類型）的例外 |
| 拋出例外且訊息相符 | 拋出指定類型的例外，而且例外訊息包含指定文字 |
| 直接失敗 | 無條件以指定訊息失敗 |

**CORE-KIT-06** 斷言失敗時的訊息必須包含：斷言標籤、期望值、實際值，格式如下（期望與實際各一行，縮排兩格）：

```
<標籤>
  期望: <期望值>
  實際: <實際值>
```

**CORE-KIT-07** 失敗訊息中的陣列或序列必須展開顯示每個元素；null 顯示為 `null`。預期要拋出例外卻沒有拋出時，實際值必須顯示「（沒有丟出例外）」；拋出的類型不對時，實際值必須顯示「<實際類型名稱>: <訊息>」。

**CORE-KIT-08** 檢查器函式庫在檢查器的建置與執行階段都必須可用，而且學生不需要另外安裝任何東西。

## 6. 終端機輸出（OUT）

### 6.1 色彩

**CORE-OUT-01** 系統必須自動判斷是否輸出色彩：只有在輸出接上互動式終端機，**而且**該終端機支援 ANSI 色碼時才開啟。支援與否的判斷規則由 Profile 定義。

**CORE-OUT-02** 指定 `--no-color` 時，必須一律不輸出色碼。

**CORE-OUT-03** 系統必須依訊息的語意上色：

| 語意 | 樣式 |
| --- | --- |
| 錯誤 | 紅 |
| 成功 | 綠 |
| 警告、`list` 的「目前」 | 黃 |
| 步驟、段落標題、指令說明 | 藍 |
| 次要說明（路徑、提示、分隔線） | 暗色（dim） |
| 標題、區塊標題 | 粗體 |

關閉色彩時，必須只輸出文字，不得殘留任何色碼。

### 6.2 編碼與替代字

**CORE-OUT-04** 系統必須以**終端機實際使用的編碼**輸出，不得假設 UTF-8；例如繁體中文 Windows 主控台的 cp950，中文必須能正確顯示。編碼的偵測方式由 Profile 定義。

**CORE-OUT-05** 輸出的文字含有目前編碼無法表示的字元時，系統必須逐字替換：

| 原字元 | 替代字 |
| --- | --- |
| `✓` | `v` |
| `✗` | `x` |
| `→` | `->` |
| `—` | `-` |
| `─` | `-` |
| 其他無法表示的字元 | `?` |

**CORE-OUT-06** 系統要求檢查器行程以 UTF-8 輸出，並以 UTF-8 讀取其輸出（CORE-VER-12）；之後再依 CORE-OUT-04、CORE-OUT-05 輸出到終端機。

**CORE-OUT-07** 系統對使用者顯示的訊息必須使用繁體中文；啟動腳本的訊息例外（CORE-BOOT-05）。

### 6.3 清畫面

**CORE-OUT-08** 清畫面只在輸出接上互動式終端機時執行，否則略過。清畫面的方式由 Profile 定義，而且必須和色彩判斷分開：不支援 ANSI 色碼的終端機也應該能清畫面。清畫面失敗時必須略過，不中止流程。

### 6.4 表格

**CORE-OUT-09** 表格必須使用下列框線格式，所有儲存格靠左對齊，每欄寬度為該欄最寬內容的顯示寬度：

```
+──────+──────+
| 欄 1 | 欄 2 |
+──────+──────+
| 內容 | 內容 |
+──────+──────+
```

**CORE-OUT-10** 計算顯示寬度時，必須略過 ANSI 色碼，並把東亞全形字元（中日韓文字、全形標點）計為 2 格。全形字元的範圍由 Profile 定義。

## 7. 啟動腳本（BOOT）

**CORE-BOOT-01** 系統必須為每個支援的作業系統提供一個啟動腳本，放在專案根目錄：Windows 一份、Linux／macOS 一份。

**CORE-BOOT-02** 啟動腳本必須在啟動 CLI 之前，確認 CLI 的建置產物是最新的：建置標記不存在，或任何 CLI 原始碼比建置標記新時，必須重新建置；否則直接啟動，不重新建置。

**CORE-BOOT-03** 重新建置失敗時，啟動腳本必須以 exit code 1 結束，不啟動 CLI。

**CORE-BOOT-04** 啟動腳本必須把所有參數原樣傳給 CLI，並以 CLI 的 exit code 結束。

**CORE-BOOT-05** 啟動腳本自己輸出的訊息必須只使用 ASCII 字元，確保在任何主控台字碼頁下都能正確顯示，而且腳本本身不需要 BOM。

**CORE-BOOT-06** 啟動腳本不得切換主控台字碼頁；編碼問題由 CLI 處理（CORE-OUT-04）。

**CORE-BOOT-07** 執行本系統只需要該技術的基本工具鏈（由 Profile 定義），不得依賴第三方套件或網路連線。

**CORE-BOOT-08** 建置產物與建置標記必須放在 `<專案根目錄>/build/`，而且不納入版本控制。

## 8. 出題者工具（TOOL）

### 8.1 自我驗證

**CORE-TOOL-01** 系統必須提供一個給出題者使用的自我驗證工具。只要下列任一項不成立，它就必須以非 0 的 exit code 結束；全部成立時以 0 結束：

0. **檔案個數**：每一題的學生可編輯檔與檢查器個數都符合 Profile 的規定，判斷規則必須與 CLI 的載入規則（CORE-FMT-03、CORE-FMT-06）相同；不符合的題目不再做後續檢查。
1. **原題一致**：每一題的原題檔都存在，而且內容和學生可編輯檔完全相同（代表 `reset` 還原得回正確的題目）。
2. **原題必敗**：每一題在未修改的狀態下，`verify` 都不通過（代表題目有意義，不是白送）。
3. **解答必過**：每一題換上參考解答後，`verify` 都通過（代表題目可解、檢查器寫對）。

**CORE-TOOL-02** 自我驗證工具必須自己重新建置 CLI，不依賴啟動腳本的增量建置。

**CORE-TOOL-03** 「解答必過」檢查必須在暫存的副本上進行（以 `--dir` 指向副本），不得修改練習目錄中的學生可編輯檔；結束後必須刪除暫存副本。

**CORE-TOOL-04** 自我驗證工具在「原題必敗」檢查開始前和全部檢查結束後，都必須執行 `reset --all`；因此執行它會清除目前的進度，但不影響原始碼。

**CORE-TOOL-05** 自我驗證工具必須逐題顯示失敗原因，最後列出所有問題的摘要（每題標註原因，例如「檔案數量不對」「缺原題」「與原題不一致」「未修改就通過」「缺解答」「解答未通過」）。

**CORE-TOOL-06** 自我驗證工具的假設前提是題目尚未被學生修改；學生改過題目之後執行，「原題一致」和「原題必敗」自然會失敗。

### 8.2 打包

**CORE-TOOL-07** 系統可以提供該技術慣用的建置工具設定，用來把 CLI 打包成單一可執行套件。打包後的版本必須與啟動腳本版本行為相同，而且檢查器函式庫必須能從該套件中取得（CORE-KIT-08）。
